## 1. 目標與定位

- 期末報告重點是「**AI**」：讓神經網路的手部辨識進入飛行控制迴路。
- 沿用實驗台的物理與控制器（SIM-CORE），只擷取需要的部分；不改動實驗台的 `index.html`。
- 操作概念：畫面右下有一顆**虛擬球**，球的轉動就是飛機的命令；手（或滑鼠）撥動球，**停止操作後球靠慣性繼續轉**。

## 2. 構想演進（為什麼最後是「虛擬球」）

| 階段 | 構想 | 結論與理由 |
|---|---|---|
| 1 | 麥克風語音 → STT → LLM → 指令 | 可行，但語音延遲 1–3 秒，只適合高層指令；API key 不能寫進公開 HTML |
| 2 | 手勢 → 固定指令（握拳 = 懸停…） | 簡單，但只是離散觸發，不是連續控制 |
| 3 | 手的位置 / 傾角 → 搖桿 | 單鏡頭只能可靠地量畫面內的 2 軸；手掌前後傾需要深度，雜訊大 |
| 4 | **虛擬球**：撥動 = 給球角速度，球的轉動 = 飛機命令 | 採用。撥動本身就是連續指令，停止就靠慣性；三個轉軸剛好對應三個控制軸 |

- 四旋翼有 6 個自由度，但只有 4 個控制輸入（欠驅動）：roll / pitch / yaw / 推力。本專案先不做高度，所以球的 3 軸就夠。
- 已有的手勢控制無人機專案大多是「手勢分類 → 指令」（kinivi/tello-gesture-control、AirSim 範例）；連續控制多用 Leap Motion 或 IMU 手套。
- 相關前例：用 2D 拖曳球面控制 3D 旋轉（Chen 1988 Virtual Sphere、Shoemake 1992 ArcBall）屬於**位置控制**；軌跡球也用於機器人遙控（Ng、Mahony、Lau 2019，纜線驅動並聯機器人）。本專案是**速率控制**（球的角速度 = 速度命令，有慣性），輸入改用一般 webcam 看指尖。整體組合沒有查到相同做法（簡單搜尋，非系統性文獻回顧）。

## 3. 系統架構

```
滑鼠 / 觸控 ─┐
             ├─► 虛擬球（角速度 ω，有慣性）─► 搖桿值 ─► Position 飛控 ─► 物理 ─► 3D 畫面
攝影機 ─► MediaPipe（手掌偵測 → 21 關鍵點 → 手勢分類）─► 挑手 ─► 映射 ─► 指尖撥球 ─┘
```

- 球的 ω → 速度命令：前後滾 = 前進速度、左右滾 = 側移、自轉 = 航向角速度。
- 飛控：Position 模式 + 定高 2 m（速度 PID → 傾斜角 → 姿態串級 PID → Mixer）。
- 球停 = 搖桿回中 = 煞車並鎖定位置。
- 物理與控制器取自實驗台 SIM-CORE：1 kHz 物理、250 Hz 控制、PX4 Quad X 編號、馬達一階延遲、四元數姿態、線性阻力。拿掉感測器誤差、Kalman、解鎖、其他飛行模式與教學面板。

座標鏈（從手到馬達）：

```
鏡頭像素 ─(鏡像判斷 χ)→ 使用者視角
鏡頭 3D (x 右, y 下, z 遠) ─(繞垂直軸 180°)→ 使用者座標 W (X 右, Y 上, Z 朝你)
W 的指尖位移 ─(以手的大小當尺)→ 螢幕上球的接觸點與位移
球面接觸 r × Δp → 球的角速度 ω（俯視：x 右、y 機頭、z 上）
ω → 搖桿 → 機頭座標速度命令 ─(繞航向角 ψ)→ NED 速度命令
→ 加速度 → 推力向量 → 傾斜角 → 姿態串級 PID → Mixer → 馬達
```

## 4. 虛擬球

### 4.1 公式

球是**俯視**畫的：螢幕 x = 右（機體右）、y = 上（機頭）、z = 朝向觀看者（機體上方）。在接觸點 r（單位球面）撥一段位移 Δp：

```
Δω = GAIN · (r × Δp)
```

- 撥球心（r ≈ (0,0,1)）→ 只有 x、y 分量 → 前後、左右滾。
- 沿邊緣切線撥（r 在赤道上）→ 只有 z 分量 → 自轉（yaw）。
- 方向慣例：往前滾（繞 x 負向）= 前進、往右滾（繞 y 正向）= 右移、俯視順時針自轉（z 負向）= 右轉。

### 4.2 手感參數

| 參數 | 值 | 說明 |
|---|---|---|
| GAIN | 1.3 | 由 1.0 調高，比較好撥 |
| 轉速上限 | 4 rad/s ↔ 3 m/s；2 rad/s ↔ 90°/s | |
| 撥動中的阻尼 | 無（撥動只加速） | 原本「球追手速」會被手的減速拖慢 |
| 放開後的阻力 | 前後左右 0.01 /s、自轉 1.5 /s | 攝影機模式下**無阻力**，握拳才停 |
| 立刻停 | 雙擊球、按住不動、空白鍵、握拳 | |

### 4.3 操作區（色塊）

球外圍有一塊淺色**操作區**。攝影機模式下，手（掌心）在色塊內才撥球；移出色塊 = 放開球，球靠慣性轉。這是「不握拳也能放手」的方式。

## 5. 攝影機 AI 手勢

### 5.1 模型架構與權重

使用 Google 官方 **MediaPipe Gesture Recognizer**（`gesture_recognizer.task`，**float16**，預訓練權重，不需自行訓練），以 WebAssembly 在瀏覽器本地執行，影像不上傳。三段神經網路串接：

| 階段 | 架構 | 輸入 → 輸出 |
|---|---|---|
| ① 手掌偵測 BlazePalm | 單階段偵測器（類 BlazeFace），編碼器-解碼器（類 FPN），focal loss，只用方形 anchor | 整張影像 → 手掌框 |
| ② 手部關鍵點 | 共用特徵提取器、三個輸出頭 | 手部裁切 → 21 點（影像座標 + 3D 公制世界座標）＋ 手存在分數 ＋ 左右手 |
| ③ 手勢分類 | 嵌入：含殘差區塊的全連接網路 → 128 維；分類：全連接網路 → 8 類 | 關鍵點 ＋ 左右手機率 → 手勢 |

- 偵測手掌而不是整隻手：手掌近似剛體，框容易估；兩手交疊時 NMS 也比較好分。
- 影片模式下沿用上一幀關鍵點推出的框來追蹤，追丟（或追蹤中的手少於 `numHands`）才重跑手掌偵測。整條流程 Pixel 6 CPU 約 16.8 ms。
- 關鍵點模型的訓練資料：約 6K 真實影像、10K 手勢影像、10 萬張合成手部；**深度標註只來自合成資料**，所以單鏡頭深度是「推估」。
- 內建 7 種靜態手勢，官方明示不支援動態手勢。本專案只用「**握拳**」（停球），撥球完全由關鍵點計算。

分工：**神經網路負責「手在哪、是什麼手勢」，本專案程式負責「手怎麼動 → 球怎麼轉」。**

### 5.2 座標對應與鏡像判斷（做錯最多次的地方）

**座標：** 使用者坐在螢幕前，鏡頭面對使用者。鏡頭座標（x 右、y 下、z 離鏡頭越遠越大）→ 使用者座標 W（X = 使用者的右、Y = 上、Z = 朝向使用者）：兩者面對面，差一個**繞垂直軸 180° 的純旋轉**（行列式 +1），右手轉完還是右手。

| 視角（舉右手、手心朝鏡頭） | 看到 | 拇指在 | 是哪隻手 |
|---|---|---|---|
| 鏡頭原始畫面 | 手心 | 右 | 右手（轉了 180°） |
| 鏡子 / 自拍鏡像 | 手心 | 左 | **左手**（反射） |
| 使用者自己的眼睛（要的效果） | 手背 | 左 | 右手 |

只翻 X 是**反射**（行列式 −1），會把右手變成左手，也就是鏡子裡的人。2D 位置和「使用者的眼睛」相同，但深度方向相反，旋轉方向（軸向量）也會反號。

**鏡像判斷（手性三重積）：** 筆電鏡頭常在驅動層先鏡像，程式要自己判斷輸入有沒有鏡像。

```
χ = −(拇指根 − 手腕) · [(小指根 − 手腕) × (食指根 − 手腕)]      （鏡頭座標下計算）
```

- 括號是右手的手背法向量（從手心穿向手背）；拇指根解剖上偏手心那側，所以真的右手 χ > 0。
- 三重積就是行列式的正負號：**旋轉不變號，反射變號**。χ > 0 = 重建出右手 = 輸入沒鏡像；χ < 0 = 輸入被鏡像過。
- 拇指攤平貼掌面時 χ ≈ 0，不可靠，所以只採用 |χ| ≥ 0.15 的幀，平滑後才切換。

```
未鏡像畫面：W = (−x, −y, z)
已鏡像畫面：W = ( x, −y, z)   （重建出來的手 x 已被反過一次）
2D 顯示一律換算成「使用者眼睛看到的」：未鏡像輸入左右翻，已鏡像輸入維持
```

> 舊版用 MediaPipe 的 Right/Left 標籤推斷鏡像（文件說它假設輸入是自拍鏡像）。實測在 tasks-vision 下判斷結果相反，虛擬手變成鏡子裡的左手，使用者還得按兩個「反轉」按鈕補償。用模型的「標籤」推斷「幾何」不可靠，所以改成直接檢查幾何。

### 5.3 映射：以手的大小當尺

| 問題 | 原因 |
|---|---|
| 球在右下角，手也得伸到鏡頭右下角 | 鏡頭座標直接放大貼到螢幕 |
| 離鏡頭越遠，虛擬手越小、撥球越不靈敏 | 大小與位移都用像素計算 |

**比例尺：** 每幀用 2D 關鍵點對 3D 世界座標（x、y）做最小平方擬合，得到 s = 鏡頭像素 / 公尺（弱透視模型的縮放）。它只跟距離有關，手傾斜不影響（直接量 2D 掌長會被透視縮短）。s 做低通（0.15），避免比例尺抖動被當成平移。

```
螢幕位置 = 球心 + (鏡頭像素 − 鏡頭中央) / s × (螢幕像素 / 公尺)
螢幕像素 / 公尺 = 0.9 × 球半徑 / 0.09 m       （手腕 → 中指根 ≈ 9 cm 畫成 0.9 個球半徑）
```

- 手在鏡頭正前方 = 虛擬手在球上；遠近都一樣大。
- 撥球位移跟著用手的大小換算，遠近手感一致。

### 5.4 撥球與轉向

5 根指尖像 5 個滑鼠游標推動球面，規則與滑鼠版相同。只用指尖在畫面上的 2D 位置，不依賴推估的深度。手的移動拆成兩部分（轉軸在手腕）：

```
phi = 指尖相對手腕的向量轉了多少（2D 剛體旋轉角）
t   = 指尖質心的移動 − 「繞手腕轉 phi 造成的移動」
```

只用質心當平移，會把扭轉誤當成平移（扭轉時轉軸在手腕，指尖質心會畫弧）。

**轉向（避免撥球時誤觸）：** 原本沿球的邊緣撥就算轉向，撥球時手指畫弧很容易誤觸。現在兩個條件都成立才算轉向：

1. **姿態門檻：** 手掌平面（手腕、食指根、小指根：剛性，比指尖穩）的法向量與 Z 夾角 < 30°，也就是手掌立起、面向螢幕（手心或手背都可）；> 40° 才退出（遲滯）。手掌平行地面時，鏡頭只看到手的側面，關鍵點互相遮擋，不適合。
2. **主導動作鎖定：** 一次推球裡，扭轉弧長 |phi| × 指尖到手腕距離 ≥ 2 × 平移，才算轉向（這次不平移）；否則只算平移，順帶的小扭轉丟掉。

方向像轉一個面向你的方向盤：逆時針 = 左轉。

**抗抖動：**

| 機制 | 做法 | 為什麼 |
|---|---|---|
| 低通 | 指尖座標 EMA 0.5 | 平滑 |
| **錨點法** | 相對錨點平移超過 0.06 個球半徑、或扭轉超過 5° 才推一次球，推完錨點移到目前位置 | 每幀死區會讓抖動累積（實測手不動 10 秒累積 119°）；錨點法下抖動只在錨點附近晃 |
| 弧長門檻 | 扭轉同時要求角度 × 指尖到手腕距離夠長 | 手指靠很近時角度容易被雜訊騙 |
| 穩定期 | 進入色塊、張開握拳、追蹤跳動、換手之後，先等 6 幀 | 手形還在變時會被誤判成撥動 |
| 跳動丟棄 | 一次跳超過 0.9 個球半徑或 45° | 追蹤失誤 |

### 5.5 多人干擾：只用最近、最大的那隻手

**問題：** `numHands: 1` 時，模型依**信心分數**挑手，不是大小。使用者的手短暫移出鏡頭，重新偵測就可能抓到後方人群的小手，之後一直追蹤它。程式端忽略它也沒用：模型只知道「已經在追 1 隻手，額滿了」，不會再去找使用者的手。MediaPipe 沒有「依大小挑選」的選項，也沒有「放掉這隻手」的 API。

**大小門檻：** 掌長（手腕 → 中指根，約 9 cm）佔畫面高度 < 12% 的手忽略，畫面顯示「手太遠」。物理意義（針孔相機模型）：

```
掌長佔畫面比例 r = L / (2 · Z · tan(VFOV/2))   →   Z = L / (2 · r · tan(VFOV/2))
一般筆電鏡頭（水平視角約 60°、4:3，tan(VFOV/2) ≈ 0.43）：Z ≈ 0.09 / (2 × 0.12 × 0.43) ≈ 0.87 m
```

- 也就是：手離鏡頭超過約 87 cm 就不算數；在那個距離，整個畫面高度涵蓋 75 cm 的真實空間。
- 同時是**抖動上限**：虛擬手的螢幕比例固定，螢幕上的抖動 ∝「1 個鏡頭像素代表幾公尺」。480p 在門檻距離約 1.6 mm/像素，掌長約 58 像素。
- 用比例而不是距離：距離需要鏡頭視角（每台裝置不同、程式讀不到）；比例直接對應「手有多少像素可用」，也就是辨識品質。

**雙辨識器切換：** 同時載入兩個辨識器，每幀只餵其中一個（推論成本不加倍，只多一份記憶體）。

| 模式 | 每幀餵 | 切換條件 |
|---|---|---|
| 1（平常） | R1（`numHands: 1`） | 追到的手太小 → 模式 2 |
| 2（有干擾） | R2（`numHands: 2`），挑最大且過門檻的手 | 只剩 1 隻夠大的手連續 0.5 秒（或沒有手）→ 模式 1 |

- 回模式 1 時小手已不在畫面：R1 記得的舊位置追不到東西 → 重新偵測 → 抓到使用者的手。
- 不用 `setOptions` 切換 `numHands`：那會重建模型的處理流程（畫面頓一下、追蹤狀態被清掉），切回時又可能先抓到小手而來回循環。
- **黏著：** 和上一幀手腕最近的那隻 = 同一隻手（回傳順序不固定）；別的手要大 1.3 倍才換過去，換手時比例尺與撥球錨點重來。

### 5.6 顯示

- **3D 虛擬手**：從使用者的手後方偏右 25°、偏上 15° 透視觀看；近粗深、遠細淡；手掌依手背法向量塗色並標「手背 / 手心」。
- **5 指平面視窗**（左上角、狀態欄底下）：
  - Newell 法依拇指 → 小指順序求指尖平面法向量（灰線；右手時從手背穿向手心）。
  - 黑棒 = 實際施加給球的力矩方向。
  - 標題列：狀態、fps、模式 1/2、偵測到幾隻手、掌長 %、推論 ms、可否轉向（手掌角度）、χ、MediaPipe 原始標籤、鏡像判斷結果。
- 手的 3D 轉動（只做顯示）：5 指尖當剛體，最小平方解 `J · Δθ = Σ aᵢ × dᵢ`（J = 指尖的轉動慣量張量）。
- 三個「反轉」按鈕（前後 / 左右 / 轉向）供實測修正正負號，記在瀏覽器；正常情況全部不需要按。

## 6. 開發中的錯誤與修正（給後續維護者）

| 現象 | 原因 | 修正 |
|---|---|---|
| 以為筆電鏡頭是原始畫面 | 筆電鏡頭在驅動層就鏡像 | 改為自動判斷 |
| 用「手往右移」校正鏡像會判反 | 手伸進畫面或停在邊緣時本身就在移動 | 改用左右手判斷（不需移動） |
| **右手顯示成鏡子裡的左手、「手心」、拇指在右；使用者要按兩個反轉按鈕補償** | MediaPipe 的 Right/Left 標籤慣例與文件相反 | 改用手性三重積 χ，不依賴標籤；反轉按鈕的記錄重設 |
| 球被手拖慢、轉不起來 | 「球追手速」= 阻尼 | 撥動只加速 |
| 手不動球也慢慢轉 | 每幀死區讓抖動累積 | 錨點法 |
| 手勢方向與球相反（多次） | 用手的 3D 轉動驅動球，又做了「翻面」「接觸物理 (−ωx, −ωy, +ωz)」，兩者都是**反射** | 改為指尖接觸（滑鼠語意）＋ 純旋轉座標對應 |
| 扭手時左右也動 | 以指尖質心當轉軸 | 轉軸改在手腕 |
| **手要伸到鏡頭右下角才碰得到球、手在邊角時偵測差** | 鏡頭座標直接放大到螢幕 | 以手的大小當尺，鏡頭中央 = 球心 |
| **撥球時常誤觸轉向** | 沿邊緣撥就算轉向，撥球的手指本來就畫弧 | 手掌面向螢幕 + 主導動作鎖定 |
| **後方人群的手搶走控制** | 模型依信心挑手，追到後不放 | 大小門檻 + R1/R2 切換挑最大的手 |
| 手機開下載的 HTML 顯示「權限被拒絕」 | 相機只在 https / localhost 開放；App 內建的 HTML 檢視器（WebView）通常不授權相機 | 放到 GitHub Pages |

## 7. 驗證方式與結果

這個開發環境連不到 CDN，3D 畫面與真實 MediaPipe 由使用者在瀏覽器實測。

1. **node 跑核心（CORE 區塊）**：模擬撥球 → 飛機反應。例：前撥一個直徑，以約 1.1–1.75 m/s 巡航，高度維持 2.00 m。
2. **無頭 Chromium + three.js 替身**：滑鼠 / 觸控事件 → 頁面狀態，無錯誤。
3. **合成手**（完整 21 點的右手）：分別模擬已鏡像與未鏡像輸入。
   - 手性 χ：未鏡像 +0.38、已鏡像 −0.38；兩種輸入還原後都是拇指在左、手背朝使用者。
   - 挑手：只有使用者 → 模式 1；R1 追到小手 → 忽略並切到模式 2；R2 同時看到小手與使用者（兩種回傳順序）→ 都選到使用者；只剩使用者 0.6 秒 → 回模式 1。
4. **使用者實機測試**（筆電鏡頭）：右手顯示為手背、拇指在左；手往右移，虛擬手也往右；前後、左右、轉向方向正確，不需按反轉按鈕。
